The Denial-of-Service Field Guide

What actually gets exhausted, and how.

Denial of service is treated as one bucket — "flood the server" — when it's really a dozen distinct mechanisms, each exhausting a different resource through a different door. This is a working reference for what those mechanisms are, organized by what breaks rather than by attack name. It's free to read. Resource exhaustion · low-rate

Slow / Low-Rate Exhaustion

These attacks don't need bandwidth — they need patience. The attacker opens a connection and feeds it data just fast enough that the server refuses to time it out, but never fast enough to let it finish. Every held-open connection ties up a thread, a worker, or a slot in the connection pool. Do that enough times and the pool empties — new, legitimate connections simply queue forever.

  • Slowloris — opens many HTTP connections and drips partial headers, one every few seconds, never completing the request.
  • Slow POST / Slow HTTP — same idea, but drips the request body instead of the headers.
  • Slow Read — sends a normal request, then advertises a tiny TCP receive window so the server's response trickles out over minutes instead of milliseconds.
  • R-U-Dead-Yet? (RUDY) — targets form submissions specifically, declaring a huge Content-Length and sending the body one byte at a time.
client opens connection → sends partial data, just under the timeout → server allocates a thread/worker and waits → connection never completes, never times out → repeat across the connection pool → pool exhausted → new clients queue → service unavailable

Resource exhaustion · connection state

Connection & State Exhaustion

Every TCP stack keeps a table of connections that are in progress or established. That table has a fixed size. Fill it with junk and real connections can't get a seat.

  • SYN flood — sends a wave of TCP SYN packets and never completes the handshake (no ACK). Each half-open connection sits in the backlog queue until it times out, and the queue is finite.
  • ACK / PUSH floods — force the target to process and validate packets against connection state it's tracking, at cost, even when the packets go nowhere.
  • Session-table exhaustion — the application-layer version: fill a load balancer's or firewall's session table rather than the OS's TCP table.

Resource exhaustion · host-local

OS / Host-Local Exhaustion

Not every DoS comes over the network. A single malicious or buggy process can take a whole machine down by exhausting something the kernel hands out: processes, threads, file descriptors, or memory.

  • Fork bomb — a process that spawns two children, each of which spawns two more, and so on, until the process table and CPU scheduler are both saturated.
  • File-descriptor / socket exhaustion — open handles and never close them until the per-process or system-wide limit is hit.
  • Memory exhaustion — allocate and never free until the OOM killer starts making decisions for you.
1 process → forks 2 → each forks 2 more (4) → each forks 2 more (8) ... → process table full, scheduler thrashing → system unresponsive, often before you can even open a shell to kill it

Roadmap: this class is about hardening your own host (ulimits, cgroups, process quotas) rather than testing a remote target — it isn't in the DoS Lab's v1 scope, which is network-facing.

Computation · algorithmic complexity

Algorithmic Complexity Attacks

This is the category most people miss, because it doesn't look like an attack at all. There's no flood, no volume — one small, entirely legitimate-looking request triggers a computation whose cost is wildly disproportionate to its size. The attacker doesn't need server access; they just need to find an input path where they control data that reaches a pathological code path.

  • ReDoS (Regular-expression Denial of Service) — a regex with catastrophic backtracking. A crafted string turns a sub-millisecond match into a computation that takes minutes or hours.
  • Billion Laughs / XML entity expansion — a small XML document where each entity references several others, expanding exponentially when parsed. Kilobytes in, gigabytes in memory out.
  • Zip bombs / decompression bombs — a small compressed file that decompresses to an enormous size.
  • Hash-collision DoS — crafted keys that all hash to the same bucket, degrading a hash table from O(1) lookups to O(n).
attacker-controlled input → HTTP / API / form field → server handler → validation / parser → vulnerable regex or parser → pathological evaluation → CPU pinned at 100% on one request → request queue grows behind it → denial of service

This is also why "just add a WAF / CDN" doesn't fully solve DoS: a reverse proxy stops volumetric floods, but it still forwards the one small request that trips the vulnerable code path underneath it.

Network & delivery · reflection

Reflection & Amplification

The attacker spoofs the victim's IP address as the source of a request sent to an open, misconfigured service — DNS resolver, NTP server, memcached, SSDP. The service replies to the (spoofed) victim, and the reply is far larger than the request. Small outbound request, huge inbound flood, and the attacker never touches the victim directly.

  • DNS amplification — a small query can return a response 20–50× larger.
  • NTP / CLDAP / SSDP / Memcached amplification — same idea, different protocol, some with amplification factors in the thousands.
  • Smurf — the classic version: spoofed ICMP echo to a broadcast address, so every host on the subnet replies to the victim at once.

What's the modern equivalent of LOIC/HOIC? Those tools are effectively dead — they rely on many willing clients flooding directly, which is trivially traced and rate-limited. What replaced them isn't a downloadable app; it's booter/stresser-for-hire services built on IoT botnets (the Mirai lineage) and reflection infrastructure, rented by the minute. The interesting research isn't "which client tool," it's which open reflectors and amplification ratios are still exploitable after a decade of BCP38 and open-resolver cleanup efforts.

Out of scope for the DoS Lab by design: reflection/amplification requires bouncing traffic off a third party, which breaks the "your target, your infrastructure only" authorization model TYPHON is built around.

Computation · application logic

Application-Logic DoS & Denial of Wallet

Sometimes the resource being exhausted isn't CPU or a socket — it's money, or a security control turned against its own users.

  • Expensive endpoints — file exports, image/video generation, unbounded search or sort — cost that scales with attacker-controlled input.
  • Account-lockout abuse — collect a list of usernames, deliberately fail login for each one, and the target's own brute-force protection locks out its real users.
  • Denial of wallet — burn through metered resources (API tokens, cloud compute, SMS credits) until the bill, not the server, is what fails. Moving to local model hosting doesn't remove this — it just moves the ceiling from a token limit to an electricity bill.

This category matters more every year because more infrastructure is metered rather than fixed-capacity — the failure mode shifts from "the server fell over" to "the invoice fell over."

Framework

Timing: The Common Thread

Nearly every category above reduces to the same core move: stretch the time window between a request arriving and its resources being freed, as far as possible. A slow attack does it by trickling data. An algorithmic-complexity attack does it by making one computation expensive. A flood does it by making the queue in front of every request longer. Framed this way, DoS stops being a grab-bag of named attacks and becomes one question applied everywhere: what stretches this timing window, and what breaks when it stretches too far?

"A denial of service is just a really easy timing attack."— James Kettle

The sharpest version of this idea is timeless timing attacks: HTTP/2 lets a client bundle multiple requests into a single packet, so the server starts them all simultaneously — eliminating the network jitter that normally drowns out microsecond-level timing differences. It turns a technique built for password recovery into a lens for finding race conditions and DoS chains that single-request testing would never surface (e.g. chaining a naive TOCTOU discount-check with a ReDoS-vulnerable field to stretch a half-second race window arbitrarily wide).

Testing Methodology Checklist

Before reaching for a tool, these are the questions worth asking about any target you're authorized to test:

  • Is the server single-threaded or synchronous? That lowers the bar for everything above.
  • Any endpoint whose response scales with attacker-controlled input size (sort, search, export, render)?
  • Does a synchronous operation (file write, lock, external call) block a request thread?
  • Can an async job queue or worker pool be exhausted by repeated job creation?
  • Any parser accepting deeply nested or recursive input (JSON/XML/zip) without limits?
  • Is rate limiting IP-based, account-based, or session-based — and how easy is it to rotate past?
  • Do account lockouts trigger fast enough, and last long enough, to be weaponized against real users?
  • Any endpoint that amplifies input (signup emails, 2FA SMS) that could be redirected at a third party?
  • Is token/session validation itself expensive (signature checks on a flood of invalid JWTs)?
